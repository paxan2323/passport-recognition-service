## 1. Rate Limiter — вердикт: не соответствует промышленному стандарту

Файл: `service/core/rate_limit.py`

- **Refill сломан математически.** Знаменатель в `elapsed` (строка ~49) — `int(1/rate_limit_rps)`,
  а TTL ключа при записи (строка ~69) — `max(2, int(burst/rate_limit_rps))`. Это разные величины.
  При дефолтах (`rps=5, burst=10`) TTL ключа = 2с, знаменатель `elapsed` = `int(1/5)=0 → max(1,0)=1`.
  Так как Redis TTL целочисленный, `elapsed` почти всегда 0 — токены не подтекают плавно.
  Реальное поведение: бёрст `burst` разрешается мгновенно, затем **полная блокировка** до истечения
  TTL (~2с), затем новый бёрст. Это не token bucket, а неудачно замаскированный fixed-window counter
  с рваным профилем throughput.
- **Не атомарно → TOCTOU race.** `check()` — это GET+TTL+GET, затем в Python вычисляется новое
  значение токенов, затем отдельный SET+INCR. Между двумя pipeline-вызовами нет `WATCH/MULTI`,
  ни тем более Lua-скрипта. При параллельных запросах с одним `api_key_id` несколько
  потоков/корутин читают одно и то же значение токенов до того, как кто-либо его декрементировал,
  и все проходят проверку `tokens >= 1`. Под конкурентной нагрузкой лимит **обходится**
  пропорционально степени параллелизма.
- **Дневной лимит** (`rate_limit_daily`) страдает тем же — GET и INCR разнесены по разным
  pipeline-вызовам, гонка возможна и здесь.
- Индустриальный стандарт для Redis-based rate limiting — единый **Lua script** (EVALSHA),
  выполняющий read-modify-write атомарно на стороне Redis, либо `redis-cell`/GCRA модуль.
  Здесь этого нет.
- **Дополнительно:** `RateLimiter`/`TaskQueue` создают отдельные Redis-клиенты без единого
  connection-pool budget — при масштабировании числа API-инстансов легко упереться в `maxclients`
  Redis.

## 2. Worker Timeout — вердикт: не соответствует, ложное чувство защищённости

Файл: `service/worker/main.py` (функция `process_task`, строки ~94–114)

```python
with ThreadPoolExecutor(max_workers=1) as pool:
    future = pool.submit(engine.recognize, image, task.min_quality)
    try:
        outcome = future.result(timeout=settings.worker_timeout_s)
    except FuturesTimeout:
        ...
        return
```

- `future.result(timeout=...)` бросает исключение в вызывающем потоке, но **не отменяет и не
  прерывает** уже запущенный поток — Python threads нельзя убить снаружи.
- `return` внутри `with` не выходит мгновенно: `ThreadPoolExecutor.__exit__` вызывает
  `shutdown(wait=True)` — воркер **физически блокируется**, пока «подвисший» вызов
  `engine.recognize()` (OpenCV/EasyOCR/torch) реально не завершится. Это может быть минуты или
  бесконечность.
- Итог: клиент получает быстрый `PROCESSING_TIMEOUT` (иллюзия отказоустойчивости), но **сам
  процесс-воркер** не берёт новые задачи из очереди всё это время → очередь растёт → через
  некоторое время `queue_max_depth=50` достигается и все клиенты получают `QUEUE_FULL`.
- Threading-таймаут для CPU-bound/native работы в Python декоративен из-за GIL и невозможности
  прервать native-код. Нужен **процесс** (изоляция на уровне ОС) либо health-check + auto-restart
  контейнера при отсутствии прогресса.
- **Утечка потоков:** новый `ThreadPoolExecutor` создаётся на каждую задачу; при зависании поток
  жив и объекты не собираются GC, пока он не завершится — при повторных зависаниях потоки/память
  накапливаются.
- **Вывод по чек-листу:** воркер не освобождается; очередь блокируется de facto; зависшие задачи
  возможны; утечка потоков — да.

## 3. Queue — вердикт: частично production-ready, есть потери данных

Файлы: `service/core/queue.py`, `service/api/routes/system.py`, `service/api/routes/recognize.py`

- **Жизненный цикл результата.** `store_result` пишет `result:*` с TTL `result_ttl_s` (300с) —
  хорошо. Но и `recognize_sync`, и `GET /v1/tasks/{id}` вызывают `queue.delete_result()` сразу
  после первого успешного чтения. Если HTTP-ответ потеряется на сети между чтением из Redis и
  доставкой клиенту, результат уничтожен безвозвратно, повторный запрос вернёт `TASK_NOT_FOUND`.
  Классическая ошибка "read = delete" вместо "read with TTL, delete по истечении TTL".
- **Нет retry/idempotency.** Клиент не может передать idempotency-key: при таймауте на своей
  стороне и повторной отправке того же файла создаётся новая задача (серверный `task_id`) →
  повторный дорогой OCR-проход, дублирование метрик.
- **Нет dead-letter очереди.** `BLPOP` атомарно вынимает `task_id` из списка; если воркер упал
  (OOM/segfault, `docker kill`) до записи результата — задача теряется полностью, requeue/DLQ нет.
- **Redis без персистентности** (`--save "" --appendonly no`, `tmpfs /data`) — осознанный
  трейд-офф ради приватности PII, но означает, что рестарт Redis теряет всю очередь и все
  in-flight результаты без возможности восстановления.

## 4. Metrics — вердикт: неконсистентно, есть двойной подсчёт

- **Двойной подсчёт `passport_rejections_total` для sync.** Инкремент происходит и в воркере
  (`_outcome_to_payload`, `worker/main.py`), и повторно в API при синхронном ответе
  (`routes/recognize.py`). Для async — только в воркере. Разная семантика метрики в зависимости от
  режима запроса.
- **Grafana-дашборд агрегирует без учёта job/instance:**
  `sum(rate(passport_rejections_total[5m])) by (reason)` суммирует серии из
  `job="passport-api"` и `job="passport-worker"` вместе → отклонения по sync-трафику показываются
  вдвое завышенными относительно реальных.
- **`api_key_id` как label у `REQUESTS_TOTAL`** — high-cardinality риск при росте числа клиентов.
- **`stats.py` парсит `/metrics` воркера через собственный regex** вместо `prometheus_client`
  parser — хрупко и дублирует стандартный функционал.
- **Блокирующий HTTP-вызов внутри async-хендлера** — `_fetch_worker_metrics` использует
  `httpx.Client` синхронно внутри `async def dashboard_stats` — блокирует event loop на до 2с при
  каждом обращении к `/api/dashboard/stats`.

## 5. Безопасность — вердикт: несколько Critical находок

- **[CRITICAL] SSRF через `webhook_url`.** `recognize_async` принимает
  `webhook_url: Optional[str] = Form(None)` без какой-либо валидации схемы/хоста. Воркер
  безусловно шлёт туда POST с распознанными PII-данными паспорта (`worker/main.py::_send_webhook`).
  Аутентифицированный клиент может указать `http://169.254.169.169/latest/meta-data/...` (cloud
  metadata), внутренние admin-эндпоинты и т.д. — классический blind SSRF из воркер-контейнера во
  внутреннюю сеть. Плюс отсутствие HMAC-подписи вебхука.
- **[CRITICAL] Grafana публично, дефолтный пароль.** `GF_SECURITY_ADMIN_PASSWORD: admin`, порт
  `3000:3000` наружу, мимо nginx (`docker-compose.yml`).
- **[CRITICAL] Prometheus публично без авторизации**, порт `9090:9090`.
- **[HIGH] `/dashboard` и `/api/dashboard/stats` без авторизации** — в отличие от `/v1/limits` и
  `/v1/tasks/{id}`, здесь нет `Depends(require_api_key)`. Отдаёт глубину очереди, число занятых
  воркеров, разбивку отказов — полезная разведывательная информация для тайминга DoS-атаки.
- **[MEDIUM] `/docs` (Swagger UI) публичен**, без сетевого ограничения в nginx.
- **[MEDIUM] Circuit breaker — process-local state**, не Redis-backed. При горизонтальном
  масштабировании API каждый инстанс видит только свою часть трафика — брейкер не откроется
  синхронно на всех репликах.
- **CORS** — явной политики нет вообще. Сейчас secure-by-default, но стоит явно
  задокументировать/зарезервировать allowlist заранее.
- **API-ключи** — сравнение через `dict.get()` не timing-safe в строгом смысле; ключи передаются
  как plaintext env var (`PASSPORT_API_KEYS`) — нет secret-manager, ротации, revocation без
  передеплоя.
- **Worker `/metrics` (9091)** и Redis (6379) не проброшены наружу — хорошо, но внутри
  docker-сети любой контейнер может достучаться без аутентификации — нет сетевой сегментации.
- **nginx** не делает rate-limit по API-ключу — только по `$binary_remote_addr`, что легко
  обходится через множество IP за одним NAT либо ботнет.

## 6. Validation — вердикт: в целом разумно, порядок проверок неоптимален

Файл: `service/core/validation.py`

- Есть magic-bytes проверка, whitelist форматов, re-encode ("сброс полиглотов") — хорошая практика.
- **Порядок проверок неоптимален:** `img.load()` (полная декомпрессия) вызывается до проверки
  `max_decode_side_px`, хотя `img.size` доступен сразу после `Image.open()` без полного
  декодирования большинства форматов.
- **Decompression bomb:** частично митигируется встроенным `PIL.Image.MAX_IMAGE_PIXELS`, но
  явного значения, согласованного с `max_decode_side_px`, не выставлено.
- Даунскейл повторно кодирует изображение — двойное копирование в памяти на каждый запрос.
- WEBP-путь не отличает animated/lossless WEBP — тихие некорректные результаты возможны.

## 7. OCR Pipeline (API ↔ Worker) — вердикт: рабочий happy path, слабая устойчивость к сбоям

- Взаимодействие через Redis List + per-task notify-list (`BLPOP`) — рабочий паттерн, атомарен на
  уровне примитивов Redis.
- Обработка ошибок воркера (`try/except Exception`) корректно не роняет процесс, но
  таймаут-путь не освобождает воркер (см. раздел 2).
- Повторная обработка отсутствует полностью — ни on уровне очереди (at-least-once с requeue), ни
  на уровне клиента (idempotency key). Единственный "retry" в системе — `RetryOcrEngine`
  (retry качества картинки, не инфраструктурного сбоя).
- Один воркер = строго последовательная обработка (`while _running: blpop → process_task`),
  масштабирование только горизонтальное, но `docker-compose.yml` не описывает автоскейлинг.
- Каждый воркер на `warmup()` загружает в память весь стек моделей — тяжёлый footprint на каждую
  реплику, нет переиспользования моделей между процессами (нет model-serving слоя).

## 8. Архитектура — race conditions / deadlock / TOCTOU / leaks

| Категория | Находка | Файл |
|---|---|---|
| TOCTOU / race | Rate limiter check-then-set без Lua/MULTI | `rate_limit.py` |
| Race | `GET /v1/tasks/{id}` + `fetch_result` + `delete_result` — не транзакция; два одновременных запроса от одного клиента гонятся за одним результатом | `system.py` |
| Resource/thread leak | Новый `ThreadPoolExecutor` на каждую задачу, поток не убивается при таймауте | `worker/main.py` |
| Event-loop starvation | Синхронные блокирующие вызовы (redis-py sync, BLPOP до 120с, httpx sync) внутри `async def` без offload — блокируют единственный event loop процесса uvicorn (самая серьёзная архитектурная проблема) | `routes/recognize.py`, `core/stats.py` |
| SPOF / state не шарится | `CircuitBreaker` — module-level singleton в памяти процесса | `circuit_breaker.py` |
| Лишние копирования | `validate_image` держит одновременно `raw`, декодированный `img`, `clean`, при даунскейле ещё `resized`+`buf2` — 3-4 полные копии изображения на запрос | `validation.py` |
| Неоптимальный алгоритм | `RateLimiter.check` — 2 pipeline round-trip'а (6 команд) там, где 1 Lua-скрипт — одна атомарная операция | `rate_limit.py` |
| Узкое место | Один Redis-инстанс без Sentinel/Cluster — SPOF для очереди, rate limit и результатов | `docker-compose.yml` |
| "Мягкий deadlock" | При падении всех воркеров каждый sync-запрос всё равно висит полный `api_sync_timeout_s` (до 120с) прежде чем вернуть таймаут — нет fast-fail | `routes/recognize.py` |

## 9. High Load (тысячи rps, десятки млн запросов/месяц, сотни клиентов)

1. **[БЛОКЕР] `uvicorn` без `--workers`, синхронный код в `async def`.** По умолчанию один процесс,
   один event loop. Внутри `recognize_sync`/`recognize_async` вызываются синхронные блокирующие
   операции: redis-py (не `redis.asyncio`), PIL/cv2 (CPU-bound), и главное —
   `queue.wait_result()` делает `BLPOP` с таймаутом до `api_sync_timeout_s` (30-120с) прямо в event
   loop. Итог: пока один sync-запрос ждёт результат, весь процесс не может обслуживать никакие
   другие запросы. Потолок — ~1 конкурентный sync-запрос на процесс, не решается одним лишь
   `--workers N`.
2. **CPU-only inference.** `MrzOcr(gpu=False)`, `RegistrationOcr(gpu=False)` жёстко захардкожены;
   в `docker-compose.yml` нет GPU passthrough. Для десятков миллионов запросов/месяц потребуются
   десятки-сотни CPU-воркеров с полным стеком моделей каждый.
3. **`RetryOcrEngine`** — до 5 проходов OCR на "слабую" зону, умноженное на число полей — worst-case
   latency непредсказуема, нет отдельного time-budget.
4. **Один Redis** — весь трафик (очередь + rate-limit + результаты) через один инстанс — SPOF и
   узкое место.
5. **`queue_max_depth=50`** — крошечный буфер для заявленной нагрузки.
6. **Нет fairness между клиентами** — общая очередь, один "шумный" клиент исчерпывает буфер для
   всех остальных.
7. **Circuit breaker не централизован** — при горизонтальном масштабировании API каждая реплика
   "открывает" свой breaker независимо.
8. **High-cardinality label `api_key_id`** в Prometheus — при "сотнях клиентов" — риск для
   Prometheus storage/perf.

**Вывод:** без пунктов 1 и 2 сервис физически не может масштабироваться линейно — это
архитектурный, а не тюнинговый вопрос.

## 10. Production Readiness — итоговая оценка

| Критерий | Оценка | Комментарий |
|---|---|---|
| Отказоустойчивость | 2/5 | Нет DLQ, нет requeue, воркер-таймаут декоративен, breaker не централизован |
| Безопасность | 2/5 | SSRF, публичный Grafana/Prometheus с дефолтным паролем, неавторизованный dashboard |
| Масштабируемость | 2/5 | Синхронный event loop в API — фундаментальный потолок; CPU-only inference |
| Наблюдаемость | 3/5 | Метрики есть, но с двойным подсчётом и high-cardinality риском; нет трейсинга |
| Логирование | 4/5 | JSON-логи, явный allowlist полей без PII — хорошая практика |
| Обработка ошибок | 3/5 | Единый каталог ошибок, консистентные коды — хорошо; retry/idempotency отсутствуют |
| Восстановление после сбоев | 2/5 | Redis без персистентности + нет DLQ = тихая потеря задач |
| Тесты | 2/5 | Только happy-path unit/lifecycle тесты; нет тестов на конкурентность, SSRF, crash-recovery |

**Итоговая оценка: не готов к production под заявленную нагрузку.** Подход к PII (TTL, отсутствие
персистентности, логи без PII) — сильная сторона. Инфраструктурный слой (concurrency-модель API,
rate limiter, worker timeout, webhook SSRF, публичный мониторинг) требует существенной доработки.

# Часть 2. Задачи на исправление (T1–T20)

## T1 — Синхронный I/O блокирует event loop API
- **Критичность:** Critical
- **Описание:** `async def`-хендлеры выполняют блокирующие вызовы (redis-py sync, `BLPOP` до 120с,
  `httpx` sync) прямо в event loop.
- **Почему проблема:** Ограничивает пропускную способность одного процесса до ~1 конкурентного
  sync-запроса; несовместимо с "тысячи rps".
- **Последствия:** Полная деградация под нагрузкой, кажущиеся "зависания" API, ложные таймауты у
  клиентов, не связанные с самим OCR.
- **Решение:** Перейти на `redis.asyncio.Redis`, переписать `TaskQueue`/`RateLimiter` на
  async-методы, использовать `await` вместо блокирующих вызовов; как временная мера — обернуть
  блокирующие вызовы в `await asyncio.to_thread(...)` и поднять `uvicorn --workers N`.
- **Архитектурные изменения:** `TaskQueue`/`RateLimiter` — async-варианты; DI-слой FastAPI —
  `async def get_queue()`.
- **Файлы:** `service/core/queue.py`, `service/core/rate_limit.py`, `service/api/routes/*.py`,
  `service/core/stats.py`, `Dockerfile.api`.
- **Зависимости:** T2 (rate limiter переписывается заодно на Lua+async).
- **Сложность:** L (3–5 дней с тестами).
- **Критерии готовности:** нагрузочный тест locust с 100+ одновременными пользователями показывает
  latency, пропорциональную реальной нагрузке воркеров, а не последовательную сериализацию в API.
- **Тесты:** locust с `--users 200 --spawn-rate 20`, замер p95/p99 при насыщенной очереди;
  unit-тест, что `/health` отвечает <50мс, пока висит долгий `/recognize`.

## T2 — Rate limiter: атомарный Lua-based token bucket
- **Критичность:** Critical
- **Описание:** Текущий rate limiter не атомарен и математически не пополняет токены (см. раздел 1).
- **Последствия:** лимиты не работают под конкурентной нагрузкой — реальная защита от abuse
  отсутствует.
- **Решение:** Единый Lua-скрипт (EVALSHA) с корректной формулой refill
  (`elapsed_real_seconds * rps`, единый источник времени — `redis TIME` или timestamp в значении
  ключа, не TTL), выполняющий read-refill-check-decrement атомарно за один RTT. Рассмотреть
  `redis-cell` (GCRA) как готовое проверенное решение вместо самописного скрипта.
- **Файлы:** `service/core/rate_limit.py` (переписать), добавить `service/core/lua/token_bucket.lua`.
- **Зависимости:** нет.
- **Сложность:** M (1–2 дня + нагрузочные тесты).
- **Критерии готовности:** параллельный тест 100 конкурентных запросов с одним ключом и `burst=10`
  пропускает ровно 10, остальные получают 429.
- **Тесты:** `pytest` с `ThreadPoolExecutor`/`asyncio.gather` на 100 параллельных вызовов `check()`,
  assert exactly `burst` allowed; долгий тест на плавность refill (не "рваный" бёрст раз в N секунд).

## T3 — Worker timeout: process-based изоляция
- **Критичность:** Critical
- **Описание:** `ThreadPoolExecutor.__exit__` блокируется на `shutdown(wait=True)` при таймауте,
  воркер не освобождается (см. раздел 2).
- **Последствия:** без фикса очередь молча деградирует при первом же зависшем изображении.
- **Решение:** Заменить `ThreadPoolExecutor` на выполнение распознавания в отдельном процессе
  (`ProcessPoolExecutor` или отдельный supervisor-процесс с `multiprocessing.Process` +
  `SIGKILL` по watchdog), либо минимально — health-check воркера по "последний прогресс N секунд
  назад" + автоматический restart контейнера при залипании.
- **Файлы:** `service/worker/main.py`, `docker-compose.yml` (healthcheck + restart policy для
  worker).
- **Зависимости:** нет.
- **Сложность:** M-L (2–4 дня, модели в `ProcessPoolExecutor` нужно грузить в каждом суб-процессе
  или шарить через shared memory).
- **Критерии готовности:** намеренно зависший mock (`time.sleep(999)`) не блокирует обработку
  следующих задач дольше `worker_timeout_s + небольшой оверхед`.
- **Тесты:** интеграционный тест — enqueue "зависающей" задачи, затем обычной; вторая должна
  обработаться в штатное время.

## T4 — SSRF через webhook_url
- **Критичность:** Critical
- **Описание:** `recognize_async` принимает произвольный `webhook_url` без валидации; воркер шлёт
  туда POST с PII без ограничений (см. раздел 5).
- **Последствия:** без фикса — SSRF из воркер-контейнера во внутреннюю сеть/cloud metadata.
- **Решение:** Валидация `webhook_url`: только `https`, запрет на приватные/link-local диапазоны
  (RFC1918, 169.254.0.0/16, ::1 и т.д.) через resolve+проверку IP перед запросом, allowlist
  доменов на уровне клиента (регистрация вебхука заранее, а не произвольный URL на каждый запрос),
  HMAC-подпись payload'а с секретом клиента, `follow_redirects=False`.
- **Файлы:** `service/core/validation.py` или новый `service/core/webhook_security.py`,
  `service/api/routes/recognize.py` (валидация на входе), `service/worker/main.py::_send_webhook`.
- **Зависимости:** нет.
- **Сложность:** M (2–3 дня).
- **Критерии готовности:** `webhook_url=http://169.254.169.254/...` и `http://localhost:6379`
  отклоняются на этапе приёма запроса (422), не доходя до воркера.
- **Тесты:** unit-тесты на IP-диапазоны (127.0.0.0/8, 10.0.0.0/8, 169.254.0.0/16, ::1, DNS
  rebinding через мок resolver).

## T5 — Публичный Grafana/Prometheus, дефолтный пароль
- **Критичность:** Critical
- **Описание:** Grafana/Prometheus проброшены наружу через `ports:` в обход nginx, Grafana с
  паролем `admin`.
- **Решение:** Убрать прямые `ports:` из docker-compose, доступ только через VPN/внутреннюю сеть
  или nginx с basic-auth/OIDC; сменить пароль на секрет из `.env`/secret-manager.
- **Файлы:** `docker-compose.yml`, `nginx/nginx.conf` (добавить `location /grafana/` с auth, если
  нужен внешний доступ).
- **Сложность:** S (несколько часов).
- **Критерии готовности:** `curl` снаружи хоста к 3000/9090 не проходит; доступ только через
  VPN/за auth.
- **Тесты:** сетевой скан (nmap) окружения после деплоя не показывает открытые 3000/9090 наружу.

## T6 — Авторизация dashboard/stats endpoints
- **Критичность:** High
- **Описание:** `/dashboard` и `/api/dashboard/stats` не требуют API-ключа, отдают операционные
  данные (глубина очереди, отказы, статус воркеров) публично.
- **Решение:** Добавить `Depends(require_api_key)` (или отдельный admin-ключ/роль); вынести
  политику "какие пути публичны" в единый явный список/middleware.
- **Файлы:** `service/api/routes/dashboard.py`.
- **Сложность:** S (1 день, включая обновление тестов).
- **Критерии готовности:** запрос без `X-API-Key` к `/dashboard` и `/api/dashboard/stats` → 401.
- **Тесты:** обновить `tests/test_service.py::TestApiEndpoints::test_dashboard_page` /
  `test_dashboard_stats` — сначала 401 без ключа, затем 200 с валидным.

## T7 — Result "read = delete" → идемпотентное чтение + idempotency-key
- **Критичность:** High
- **Описание:** Результат удаляется из Redis сразу при первом чтении; клиент не может передать
  idempotency-key для дедупликации ретраев.
- **Решение:** Не удалять результат при первом чтении — полагаться на TTL (`result_ttl_s`);
  добавить опциональный `Idempotency-Key` заголовок от клиента → маппинг key→task_id в Redis с TTL,
  чтобы повторный запрос с тем же ключом не создавал новую задачу.
- **Файлы:** `service/core/queue.py`, `service/api/routes/recognize.py`,
  `service/api/routes/system.py`, `service/core/schemas.py` (добавить поле).
- **Сложность:** M (2–3 дня).
- **Критерии готовности:** повторный `GET /v1/tasks/{id}` после первого успешного чтения всё ещё
  возвращает результат (в пределах TTL); повторный POST с тем же `Idempotency-Key` не создаёт
  вторую OCR-задачу.
- **Тесты:** расширить `test_service_lifecycle.py` — двойной fetch результата, тест с повторным
  idempotency-key.

## T8 — DLQ / requeue при крахе воркера
- **Критичность:** High
- **Описание:** При падении воркера после `BLPOP` (задача уже вынута из списка) задача теряется
  без возможности восстановления.
- **Решение:** Использовать надёжный паттерн очереди — `BLMOVE`/`LMOVE` в
  `processing:{worker_id}` список вместо простого `BLPOP` из общего списка + периодический reaper,
  который переносит "зависшие" (по heartbeat) задачи обратно в очередь или в DLQ с алертом.
- **Файлы:** `service/core/queue.py`, `service/worker/main.py`.
- **Сложность:** L (3–5 дней).
- **Критерии готовности:** `docker kill -9` воркера в момент обработки → задача автоматически
  переставляется в очередь (или уходит в DLQ с видимой метрикой) в течение конфигурируемого
  таймаута.
- **Тесты:** chaos-тест — убить контейнер воркера во время обработки, проверить, что задача не
  потеряна.

## T9 — Метрики: убрать двойной подсчёт, единая семантика sync/async
- **Критичность:** Medium
- **Описание:** `REJECTIONS_TOTAL` инкрементится дважды для sync-режима (воркер + API), но один раз
  для async; Grafana суммирует без разбивки по job.
- **Решение:** Инкрементировать `REJECTIONS_TOTAL` только в воркере (единственный источник истины
  для результата задачи); API инкрементирует только "транспортные" отказы (auth, rate-limit,
  validation, timeout), которые воркер физически не видит. Добавить `job`/`source` label и
  обновить Grafana-запрос с явной группировкой `by (reason, job)` либо `sum without (instance)`.
- **Файлы:** `service/api/routes/recognize.py`, `service/worker/main.py`,
  `monitoring/grafana/dashboards/passport-service.json`.
- **Сложность:** S (1 день).
- **Критерии готовности:** нагрузочный тест с известным числом намеренных отказов даёт ровно
  совпадающее число в дашборде.
- **Тесты:** unit-тест на подсчёт (мок Prometheus registry), snapshot-тест grafana JSON.

## T10 — Circuit breaker → централизованное состояние (Redis)
- **Критичность:** High (для сценария масштабирования)
- **Описание:** Breaker хранит состояние в памяти процесса, не синхронизируется между репликами
  API.
- **Решение:** Перенести breaker state в Redis (sorted set временных меток исходов + атомарный
  Lua-скрипт для открытия/закрытия), чтобы все реплики API видели единое состояние.
- **Файлы:** `service/core/circuit_breaker.py`.
- **Сложность:** M (2 дня).
- **Критерии готовности:** при 2+ репликах API breaker открывается одновременно на всех при
  превышении порога.
- **Тесты:** интеграционный тест с двумя инстансами `TestClient`, общий Redis, breaker открывается
  синхронно.

## T11 — Fast-fail при полностью недоступных воркерах
- **Критичность:** Medium
- **Описание:** При отсутствии живых воркеров клиент всё равно ждёт полный `api_sync_timeout_s`
  (30–120с) прежде чем получить ошибку.
- **Решение:** Дешёвая проверка "жив ли хоть один воркер" (по `WORKERS_BUSY`/heartbeat в Redis с
  коротким TTL, обновляемым воркером) перед постановкой в очередь — если воркеров 0 за последние
  N секунд, сразу возвращать `503 QUEUE_FULL`/новый код `NO_WORKERS_AVAILABLE`.
- **Файлы:** `service/worker/main.py` (heartbeat), `service/api/routes/recognize.py`.
- **Сложность:** S-M (1–2 дня).
- **Критерии готовности:** при остановке всех воркеров `POST /recognize` отвечает за <1с, а не за
  30–120с.
- **Тесты:** остановить worker-сервис, замерить время ответа API.

## T12 — Idempotency-key для клиентских ретраев
- **Критичность:** Medium
- **Описание:** См. T7 — если T7 реализуется без idempotency-key, вынести отдельно.
- **Решение/файлы/тесты:** идентичны части T7, касающейся `Idempotency-Key`.

## T13 — Бюджет времени на RetryOcrEngine
- **Критичность:** Medium
- **Описание:** До 5 проходов OCR на "слабую" зону без общего time-budget — непредсказуемый
  worst-case latency.
- **Решение:** Передавать в `RetryOcrEngine` общий deadline (например, оставшееся время до
  `worker_timeout_s`) и прерывать перебор вариантов препроцессинга при его исчерпании, а не только
  по числу вариантов.
- **Файлы:** `postprocess/retry_ocr.py`, `service/core/engine.py`.
- **Сложность:** S (1 день).
- **Критерии готовности:** документ с 10 "слабыми" зонами не превышает согласованный p99 latency.
- **Тесты:** синтетический документ со всеми размытыми зонами, замер worst-case latency.

## T14 — CPU→GPU inference path для масштабирования
- **Критичность:** High (стратегически, не срочно)
- **Описание:** Инференс жёстко захардкожен на CPU (`gpu=False`), нет GPU passthrough в
  docker-compose — потолок throughput далёк от целевой нагрузки.
- **Решение:** Добавить GPU-профиль docker-compose (`deploy.resources.reservations.devices` +
  `gpu=True` конфигурация), рассмотреть выделенный model-serving слой (Triton/TorchServe) с
  батчингом запросов вместо per-request инференса в каждом воркер-процессе.
- **Файлы:** `docker-compose.yml`, `service/core/engine.py`, `postprocess/factory.py`.
- **Сложность:** XL (стратегическая инициатива, недели).
- **Критерии готовности:** throughput на GPU-воркер измерен и документирован, есть capacity-план
  под заявленную нагрузку.

## T15 — Per-client fairness в очереди
- **Критичность:** Medium
- **Описание:** Общая очередь без партиционирования — один клиент может исчерпать
  `queue_max_depth` для всех остальных.
- **Решение:** Партиционировать очередь по client_id (round-robin между несколькими списками) или
  ограничить долю `queue_max_depth`, занимаемую одним клиентом.
- **Файлы:** `service/core/queue.py`.
- **Сложность:** M.
- **Критерии готовности:** нагрузочный тест — один клиент шлёт 1000 запросов, другой клиент
  продолжает получать обслуживание в разумное время.

## T16 — Порядок проверок в validate_image + explicit MAX_IMAGE_PIXELS
- **Критичность:** Low-Medium
- **Описание:** `img.load()` вызывается до проверки размера — лишняя работа/декомпрессия для
  заведомо отклоняемых изображений.
- **Решение:** Проверять `img.size` сразу после `Image.open()` (до `img.load()`), выставить
  `PIL.Image.MAX_IMAGE_PIXELS` явным значением, согласованным с `max_decode_side_px`.
- **Файлы:** `service/core/validation.py`.
- **Сложность:** S (несколько часов).
- **Критерии готовности:** тест с "маленьким файлом, большим заявленным разрешением" отклоняется
  без полного декодирования (замер CPU/времени).

## T17 — Асинхронный сбор worker-метрик в dashboard
- **Критичность:** Medium
- **Описание:** `_fetch_worker_metrics` использует sync `httpx.Client` внутри async-хендлера —
  блокирует event loop.
- **Решение:** Заменить на `httpx.AsyncClient`, либо кэшировать результат на короткое время
  (2–5с) и отдавать stale-while-revalidate.
- **Файлы:** `service/core/stats.py`.
- **Сложность:** S.
- **Критерии готовности:** `/api/dashboard/stats` не блокирует параллельные запросы к другим
  эндпоинтам.

## T18 — Явная CORS-политика
- **Критичность:** Low
- **Описание:** CORS не сконфигурирован явно — риск, что в будущем кто-то добавит
  `allow_origins=["*"]` необдуманно.
- **Решение:** Явно задокументировать/закодировать политику (allowlist origins или явный отказ от
  CORS).
- **Файлы:** `service/api/main.py`.
- **Сложность:** S.

## T19 — Secret management для API-ключей
- **Критичность:** Medium
- **Описание:** `PASSPORT_API_KEYS` — plaintext env var, без ротации/revocation без передеплоя.
- **Решение:** Вынести ключи в secret-manager (Docker secrets/Vault/SOPS), либо хранить активные
  ключи в Redis с TTL/версионированием вместо статичного env — для ротации без передеплоя.
- **Файлы:** `service/core/config.py`, `service/core/auth.py`, `docker-compose.yml`.
- **Сложность:** M.

## T20 — Тестовое покрытие concurrency/security сценариев
- **Критичность:** Medium (предотвращает регрессии всех вышеперечисленных фиксов)
- **Описание:** Текущие тесты (`tests/test_service*.py`) покрывают только happy path, поэтому баги
  T1–T4 не были пойманы раньше.
- **Решение:** Добавить тесты на: конкурентный rate limiter (T2), SSRF-валидацию webhook (T4),
  crash-recovery воркера (T8), event-loop non-blocking поведение (T1), нагрузочные
  locust-сценарии как часть CI.
- **Файлы:** `tests/test_rate_limit_concurrency.py` (новый), `tests/test_webhook_security.py`
  (новый), `tests/test_worker_crash_recovery.py` (новый).
- **Сложность:** M-L.

# Executive Summary

Сервисный слой имеет здравую доменную модель (чёткий каталог ошибок, разделение sync/async,
TTL-based приватность PII, структурированные JSON-логи без чувствительных полей, разумная
арбитражная логика распознавания) — это сильная база. Но на уровне инфраструктурной надёжности и
безопасности обнаружен ряд критических дефектов, часть из которых (блокирующий event loop,
сломанный rate limiter, декоративный worker-timeout) означают, что заявленная цель — "тысячи rps,
десятки миллионов запросов в месяц, сотни клиентов" — физически недостижима на текущей архитектуре
без переработки concurrency-модели API и стратегии инференса (CPU→GPU/батчинг). Отдельно —
публично экспонированные Grafana/Prometheus с дефолтным паролем и SSRF через webhook — это
эксплуатируемые уязвимости уровня Critical, требующие немедленного исправления вне зависимости от
планов по нагрузке. Общая оценка: функционально работоспособный MVP, не готовый к промышленной
эксплуатации без 2–3 спринтов доработок.

# Architecture Roadmap

**Срочно (эта неделя):**
- T4 (SSRF) — эксплуатируемая уязвимость.
- T5, T6 (публичный мониторинг/дашборд) — эксплуатируемая уязвимость.
- T3 (worker timeout) — прямой риск полной остановки обработки.

**Ближайший спринт:**
- T2 (rate limiter на Lua) — без этого лимиты не защищают систему.
- T1 (async event loop) — начать с `asyncio.to_thread` обёрток как временная мера + `--workers N`,
  полноценный `redis.asyncio` — как следующий шаг того же эпика.
- T7 (idempotent read), T9 (метрики), T11 (fast-fail).

**Среднесрочные улучшения (1–2 месяца):**
- T8 (DLQ/requeue), T10 (централизованный circuit breaker), T13 (time-budget для retry OCR),
  T15 (fairness), T19 (secret management), T20 (тесты).

**Долгосрочные архитектурные изменения:**
- T14 — переход на GPU/batched model-serving (Triton/TorchServe) вместо модели "процесс = полный
  стек моделей".
- Kubernetes + HPA по глубине очереди (KEDA autoscaler на Redis List length) вместо статичного
  числа реплик в docker-compose.
- Redis Sentinel/Cluster вместо единственного инстанса.
- Полноценный distributed tracing (OpenTelemetry) через API→Redis→Worker.

# Дополнительные улучшения (идей нет в текущем коде)

- **HMAC-подпись webhook'ов** (`X-Signature` заголовок с HMAC-SHA256 по секрету клиента) —
  стандарт для webhook-провайдеров (Stripe/GitHub-style), заодно снижает риск T4.
- **KEDA/HPA автоскейлинг воркеров по `passport_queue_depth`** вместо ручного числа реплик —
  критично для "десятков миллионов запросов/месяц" с неравномерной нагрузкой.
- **Батчинг OCR-инференса** — накапливать мини-батч (десятки мс ожидания) и прогонять через
  модель батчем — особенно эффективно на GPU.
- **Отдельный "fast reject" pre-classifier** (маленькая быстрая модель) прямо в API-слое для
  мгновенного отсева совсем нерелевантных изображений до постановки в тяжёлую очередь.
- **WAF перед nginx** (Cloudflare/AWS WAF) — защита от L7 DDoS до `limit_req_zone`.
- **Chaos engineering в CI** — регулярный прогон сценариев "убить воркер", "убить Redis",
  "задержка сети", чтобы баги вроде T3/T8 ловились автоматически.
- **Data retention/compliance слой** — формализовать политику хранения (частично уже есть через
  TTL) плюс аудит-лог обращений к распознанным PII (для соответствия 152-ФЗ и аналогам).
- **Ролевая модель в Grafana** (viewer vs admin) вместо единственного admin-аккаунта.
- **gRPC/HTTP2 между nginx↔API** для снижения оверхеда на большом числе одновременных соединений.
- **Версионирование моделей в ответе API** — добавить `model_version` в `DocumentBlock`, чтобы
  различать качество между релизами дообученных сетей.
- **Явный SLA/SLO документ** — формализовать целевые p95/p99 latency и error budget для будущих
  архитектурных решений (например, обоснование перехода на GPU).
