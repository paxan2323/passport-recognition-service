# План v4 — чат поддержки как ядро + программа «нативного ощущения»

> Для AI-агента. Дата: 2026-07-05. Ничего не менять до утверждения этого плана.
> Контекст: пересборка (v2) и полировка (v3) выполнены; zero-based аудит
> (`x5revision-saas/docs/audit/EXECUTOR_ZERO_BASED_REDESIGN_AUDIT_2026-07-05.md`) дал вердикт
> «refactor, не rebuild». Этот план закрывает два самых больных остатка:
> **(A)** нет полноценного чата с менеджером — вместо него local mailto;
> **(B)** приложение «не чувствуется» — веб-страница, а не инструмент в руке.

---

## ДИАГНОЗ (факты из кода, не мнения)

### A. Почему сейчас «почта» и где на самом деле чат

| Факт | Где |
|---|---|
| Полная модель чата **уже есть**: `MessageThread` (один тред на исполнителя в тенанте) + `Message` (sender_kind manager/executor/client, привязка к слоту, `read_at`) | `tenant/models/_comms.py:237-351` |
| Endpoints исполнителя есть: GET/POST `/messages/`, POST `/messages/read/` | `tenant/views/executor_comms.py:156-225` |
| Менеджерская сторона есть: `/comms/messages` в tenant-admin; ответ из тикета поддержки уходит в тот же DM-тред | `tenant-admin/.../comms/messages/messages-content.tsx`, `SUPPORT_MODULE_REDESIGN_PLAN_2026-06-29.md` §0 |
| Live-доставка есть: SSE `message_created` инвалидирует кэш чата | `use-executor-events.ts:38-41` |
| **Но всё это за фиче-флагом `direct_messages`**, и когда он выключен — исполнитель видит «Помощь» | `executor_comms.py:158`, `messages-screen.tsx:204-225` |
| Fallback «Написать в поддержку» — это `mailto:` на `NEXT_PUBLIC_SALES_CONTACT_EMAIL \|\| support@workforce.app` — **email вендора платформы (sales-контакт!), не менеджера организации** | `help-screen.tsx:8-9,34-41` |

Вывод: чат не «отсутствует» — он **выключаем**, а его fallback маршрутизирует вопросы
грузчика Твери в почту отдела продаж платформы. Проблема продуктовая (политика канала),
а не «надо написать чат-модуль с нуля».

Чего чату не хватает до «полноценного модуля» (реальные гэпы):

1. **UI — лента карточек, не чат**: page-scroll вместо inverted-списка, composer не привязан
   к клавиатуре (visualViewport), нет optimistic-отправки, нет статусов «отправляется/доставлено/
   не ушло — повторить», нет разделителей дат и разделителя «Непрочитанные».
2. **Нет вложений**: у `Message` нет поля файла (фото есть только у инцидентов). «Пришли фото
   пропуска/полки/накладной» — базовый сценарий полевой поддержки.
3. **Нет пагинации**: GET `/messages/` отдаёт весь тред целиком — деградация на старых тредах.
4. **Нет пуша о ответе менеджера** с deep-link в чат (SSE работает только при открытом приложении) — проверить, что notifications-модуль шлёт web-push на `message_created`; если нет — гэп.
5. **Личность менеджера скрыта**: `sender_user` есть в модели, но сериализация исполнителю
   отдаёт только `sender_kind` → в UI безликий «Диспетчер».
6. Инциденты и чат живут раздельными вкладками, хотя на бэке ответ на инцидент уже падает в DM-тред.

### B. Почему «не чувствуется» (главные виновники, по убыванию)

1. **Каждый переход таба ремаунтит весь экран**: `shell.tsx:22` —
   `<div key={pathname} className="v2-tab-enter">` + анимация 200ms. Любой тап по табу =
   полный перерендер, потеря позиции скролла, fade-заглушка. Нативные приложения хранят
   состояние таба; у нас — «перезагрузка страницы» на каждый тап. Это ощущение «веба» №1.
2. **Boot-водопад**: 9 API-вызовов до спокойного экрана (`tenant-info, refresh, me, slots,
   wallet, esign, passkey, earnings, events`) — на 3G секунды скелетонов.
3. **Нет optimistic UI вне офлайн-очереди**: бронь смены, отправка сообщения, отметка
   прочтения ждут сервер → интерфейс «думает» вместо мгновенной реакции.
4. **Haptics написаны, но не подключены**: `lib/haptic.ts` (tap/success/warning/error) —
   используется один раз (отправка сообщения). Чек-ин, slide-to-confirm, ошибки — немые.
5. **Pull-to-refresh существует** (`shared/pull-to-refresh.tsx`), но не подключён ни к одному
   v2-экрану — обновление только невидимым поллингом.
6. **Нет свайп-жестов**: back-жеста на под-экранах нет (профиль-секции на query-params его
   ломают — см. аудит Z-15), свайпа между сегментами нет.
7. **PWA-поверхность не добита**: нет Badging API (число на иконке приложения), нет
   app shortcuts на «Чат»/«Смены», splash по умолчанию.

## РЕШЕНИЯ (что утверждаем до начала работ)

**R1. Чат — базовая возможность, а не опция.** Флаг `direct_messages` переводится в
default-on для всех тенантов (выключение остаётся возможным, но осознанным действием
владельца тенанта). «Помощь» исполнителя **никогда** не показывает `mailto:` — email
остаётся каналом «менеджер тенанта ↔ поддержка платформы», работника он не касается.
Без чата (тенант выключил явно) помощь показывает телефон диспетчера и FAQ — без почты.

**R2. Один тред на исполнителя — сохранить.** Никаких «тикетов» на стороне работника:
тикеты/очереди/SLA — менеджерская проекция того же потока (это уже направление
`SUPPORT_MODULE_REDESIGN_PLAN`). Инциденты становятся **структурированной карточкой внутри
чата** (тип+фото+статус), вкладка «Инциденты» упраздняется после миграции.

**R3. Таб «не перезагружается».** Состояние и скролл каждого таба живут между переключениями;
анимация перехода — только на push-навигации вглубь (деталка, чат), не на смене таба.

**R4. Каждое действие отвечает мгновенно.** Правило: визуальный отклик ≤ 1 кадра (optimistic
или локальный state), сервер догоняет; ошибка = откат + понятный retry. Уже реализовано
для чек-ин/аут (офлайн-очередь) — распространить на бронь, сообщения, прочтение, отгулы.

**R5. Ничего не менять сейчас.** Этот документ — приёмочная спецификация; работы стартуют
по этапам ниже после утверждения R1–R4 (R1 требует продуктового решения владельца).

## WORKSTREAM A — Чат поддержки исполнителя

### Целевой экран `/messages` (чат)

```
┌──────────────────────────────┐
│ ← Мария · менеджер      ⋯    │  identity: имя+инициалы из sender_user; офлайн-пилюля
│──────────────────────────────│
│        · 3 июля ·            │  разделитель дат
│ ┌──────────────────┐         │
│ │ Смена перенесена │         │  менеджер: слева, surface
│ └──────────────────┘         │
│   ── Непрочитанные ──        │  unread-разделитель, автоскролл к нему
│         ┌──────────────────┐ │
│         │ Приду к 10:15  ✓✓│ │  я: справа, brand-tonal; ✓ отправлено ✓✓ прочитано
│         └──────────────────┘ │
│         ┌──────────────────┐ │
│         │ [фото] Накладная ⏱│ │  optimistic: ⏱ → ✓; ошибка: «Не ушло · Повторить»
│         └──────────────────┘ │
│ ⚠ Карточка инцидента: статус │  инцидент = структурное сообщение (R2, фаза A3)
│──────────────────────────────│
│ [Уже в пути][Опоздаю][Вопрос]│  quick-чипы (есть) — над composer
│ [📎] [Напишите…        ] [➤] │  composer прижат к visualViewport, не к таб-бару
└──────────────────────────────┘
```

Поведение: inverted-список (новые снизу, скролл прибит к низу), пагинация вверх по курсору;
вход в чат помечает видимые сообщения прочитанными (batch `messages/read/`); при офлайне
сообщение уходит в существующую очередь (`offline-queue.ts`, новый тип `message`) с ⏱;
push «Мария ответила: …» → deep-link `/messages`. Слот-контекст (уже отправляется) рендерится
чипом «к смене 5 июля · Тверская» над пузырём.

### Задачи A (backend → frontend, последовательно)

**A0 · Продуктовое решение R1** — включение `direct_messages` default-on + текст помощи без
mailto. Затрагивает: `platform_app/tenant_product_settings.py` (дефолт), миграция значений
тенантов, `help-screen.tsx`. DoD: на свежем тенанте чат доступен без настройки; в UI
исполнителя нет ни одного `mailto:`; email вычищен из env исполнительского приложения.

**A1 · Message attachments** — поле `attachment` (image, валидация размера как у инцидентов)
+ выдача URL в сериализаторе + multipart в POST `/messages/`. DoD: фото уходит/отдаётся обеим
сторонам; в tenant-admin чате отображается; EXIF-strip как в инцидентах.

**A2 · Пагинация + identity** — курсорная выдача (`?before_id=`, 50 шт) + `sender_name`
(имя менеджера) в сериализации исполнителя. DoD: тред 1000+ сообщений открывается < 300ms;
UI показывает имя и инициалы менеджера.

**A3 · Чат-UI по спеке выше** — переписать messages-tab: inverted-список, пузыри, статусы
✓/✓✓/⏱/ошибка, unread-разделитель, даты, composer на visualViewport, optimistic через
react-query `onMutate`, офлайн-тип `message` в очереди. Инциденты: создание остаётся шитом,
карточка результата — в ленте чата; вкладка «Инциденты» скрывается при пустой истории.
DoD: отправка отображается ≤ 1 кадра; reload не теряет optimistic-сообщения (очередь);
клавиатура не перекрывает composer на iOS/Android; скриншоты light/dark.

**A4 · Push на ответ менеджера** — web-push `message_created` (если notifications-модуль уже
шлёт — только deep-link и копия), title «{имя} · {tenant}», tap → `/messages`. DoD: свёрнутое
приложение получает пуш ≤ 5 с после ответа менеджера; тап открывает чат на unread-разделителе.

**A5 · Бейджи** — unread чата: точка+число на bell во всех табах (после глобального app-bar
из аудита T-04) + **Badging API** (`navigator.setAppBadge`) на иконке PWA. DoD: непрочитанное
видно с любого экрана и с домашнего экрана телефона.

Связь с менеджерской стороной: очереди/SLA/массовые действия — по `SUPPORT_MODULE_REDESIGN_PLAN_2026-06-29.md`,
здесь не дублируются. Требование синхронизации одно: ответ на инцидент и на DM — один тред (уже так).

## WORKSTREAM B — Программа «нативного ощущения»

### B1 · Живые табы (главный фикс восприятия)
Убрать `key={pathname}` + `v2-tab-enter` из `shell.tsx`; сохранять скролл и состояние таба
(в идеале — parallel route slots / кэш скролл-позиций per-tab; минимум — восстановление
scrollTop). Анимация остаётся только на push-переходах вглубь (деталка смены, чат, live) —
slide-in 200ms с жестом возврата.
**DoD:** переключение «Смены → Деньги → Смены» возвращает на ту же позицию скролла без
перерисовки-вспышки; переключение таба < 100ms на среднем Android; видеозапись до/после.

### B2 · Optimistic всё
Бронь/отклик на смену, отгул, оспаривание штрафа, прочтение объявлений: мгновенный UI +
`onMutate`/rollback + toast-undo где уместно (бронь уже задумана с undo в плане v2 — довести).
**DoD:** ни одного действия, где кнопка «думает» со спиннером дольше кадра при живой сети;
таблица действий × поведение (успех/ошибка/офлайн) в PR.

### B3 · Haptics-карта + микроотклик
Подключить существующий `haptic.ts`: tap — все primary-кнопки и табы; success — чек-ин/аут,
отправка; warning — slide-to-confirm на пороге; error — ошибки отправки. Slide-to-confirm:
тик на каждые 25% прогресса. Уважать `prefers-reduced-motion` и настройку (выключатель в
Настройках).
**DoD:** карта «событие → паттерн» в коде одним модулем; ручной чек-лист Android/iOS.

### B4 · Жесты
Pull-to-refresh (компонент уже есть) на 4 табах; swipe-back на под-экранах (истории
браузера достаточно — главное перевести секции профиля/money на под-роуты, задачи T-07/teardown
аудита); горизонтальный свайп WeekStrip уже есть — добавить инерцию к сегментам «Мои/Свободные».
**DoD:** pull-to-refresh везде с haptic-порогом; back-жест Android возвращает на хаб, не выкидывает из приложения.

### B5 · Скорость холодного старта
Boot-diet (аудит T-12): до first paint — только `tenant-info/refresh/me/slots`; остальное
после interactive. Preload шрифта Inter (уже next/font — проверить swap), code-split live-экрана
и QR-сканера, `<Link prefetch>` на табы.
**DoD:** LCP < 2.5s на Fast 3G / средний Android (Lighthouse CI до/после в PR); скелетон
не «мигает» при тёплом кэше (показывать только после 150ms задержки).

### B6 · PWA-глубина
App shortcuts (manifest: «Смены», «Чат», «Деньги»), Badging API (из A5), splash-иконки
maskable (есть — проверить), `overscroll-behavior-y: none` на shell (убрать резиновый
скролл-хром), `user-select:none` на интерактивных, `-webkit-tap-highlight-color: transparent`.
**DoD:** установленное приложение неотличимо от нативного по хрому: нет синего тап-хайлайта,
нет резинки на краях, на иконке — бейдж непрочитанного.

## МЕТРИКИ ПРИЁМКИ ПРОГРАММЫ

- Переключение таба: < 100ms, позиция скролла сохранена, 0 remount-анимаций.
- Отправка сообщения: пузырь ≤ 1 кадра; офлайн — ⏱ и авто-доотправка; ответ менеджера
  при свёрнутом приложении — push ≤ 5 с с deep-link.
- В UI исполнителя: 0 `mailto:`, 0 упоминаний email.
- INP p75 < 200ms; LCP Fast-3G < 2.5s.
- Каждое интерактивное: pressed-state + haptic по карте B3.
- Видео-протокол сдачи каждого этапа: 30-сек запись до/после на среднем Android.
